31. Bills use immutable order-price snapshots, exclude REJECTED/CANCELLED lines and snapshot venue service/VAT settings when the bill is first created. Changing a venue setting does not silently change an existing bill. Integer half-up basis-point rounding uses BigInt intermediates. The configured tax base includes service charge; included VAT is disclosed without adding it twice. This is an implementation assumption pending the source documents' tax/fiscal confirmation gate, not a statement of the legally applicable tax treatment. No production tax settings are certified.
32. Bill versions change only when financial inputs change, not on a repeated read. Orders and bill.updated outbox events are committed together and replayed idempotently. Reducing a bill below already-paid funds requires refund review.
33. Source conflict for forthcoming splits: Backlog US-305 says lock expiry reopens the split, while the architecture state diagram says EXPIRED. Follow the explicit automated acceptance criterion and reopen to OPEN when no payment is in flight, preserving paid shares. The backlog's separate pending bill is represented as a separate pending-balance segment because the provided schema permits one bill/session and the architecture explicitly keeps new orders on that bill with an unchanged locked split.

34. Equal splits apply to the unpaid balance, use a persisted 0-based slot index and the source's deterministic remainder rule, with the schema's 50-payer maximum. Zero-value slots require no provider payment and must be labelled accordingly in the payment UI. Unpaid OPEN recalculation creates a new draft and cancels the old one; paid drafts cannot be silently replaced.
35. Billing child tables gain explicit venue/session scope keys and composite foreign keys rather than relying on unscoped identifier lookups. 36. Itemized PUT updates only the supplied shares. The creator may initialise unbound shares for same-session participants to support the architecture example, but cannot subsequently release another participant's owned share. Exact unchanged entries are permitted for safe retries. Claiming a slot is atomic and does not change its amount. All allocation writes recheck session activity under the venue transaction.
37. Partial itemized claims do not consume all proportional extras prematurely: floors are assigned to claimed bases, and the largest-remainder completion runs only when all base is allocated. The API exposes unassigned base separately from unassigned gross. Prior paid item portions are subtracted through a venue/session-scoped SQL aggregate. A remaining fee-only balance uses EQUAL rather than pretending it has unclaimed items. Schema legacy/paid-ledger discrepancies fail for review.

38. Split writes explicitly acquire the scoped PostgreSQL split row FOR UPDATE in addition to the venue advisory lock, as required by the supplied allocation trigger. 39. An EQUAL lock assigns immutable base-item portions to shares by exact largest-remainder apportionment, then stable item-ID order.
