26. Waiter calls deduplicate all table requests within 60 seconds, irrespective of participant/reason, under a per-venue transaction. KITCHEN/BAR can read alerts; only WAITER/MANAGER/OWNER can acknowledge. Same-actor acknowledgement is idempotent; another actor sees a conflict. Message retention and resolution/expiry jobs require operational implementation before launch.
27. Guest SSE uses bearer authentication rather than query-string JWTs. A broker reads the durable log in bounded batches per venue; Redis notifies and a five-second venue-level poll recovers missed notifications. Initial replay queues live events and captures its upper cursor after subscribing to avoid a connection race. Streams contain only the guest session and explicit public menu-availability events. Capacity limits/backpressure protection exist; target load and cross-node latency are unverified.

28. Guest session initialization includes the venue theme and an explicit sample-data flag. The demo seed is tagged; normal owner venues remain untagged. Typography and theme tokens are shared, page styles are app-specific. Native guest/cart dialogs and measured floating-action spacing support enlarged text and short/folded layouts.
29. A closed/expired guest stream stops the session flow and requires explicit re-entry; it never silently joins a new table session. Bearer SSE uses low fetch priority. Incomplete Lighthouse reports are rejected, and bundle-only checks validate JS independently instead of supplying a synthetic zero LCP. Reported metrics reference actual built JS files and the sample fixture.
30. Guest storage denial falls back to current-tab storage/in-memory state and shows a notice to keep the page open until confirmation. HTTP replies cannot regress an acknowledged waiter call or replace a newer call with an older request. Browser snapshots capture implementation regressions; physical folds/hinges remain unverified.

31. Bills use immutable order-price snapshots, exclude REJECTED/CANCELLED lines and snapshot venue service/VAT settings when the bill is first created. Changing a venue setting does not silently change an existing bill. Integer half-up basis-point rounding uses BigInt intermediates. The configured tax base includes service charge; included VAT is disclosed without adding it twice. This is an implementation assumption pending the source documents' tax/fiscal confirmation gate, not a statement of the legally applicable tax treatment. No production tax settings are certified.
32. Bill versions change only when financial inputs change, not on a repeated read. Orders and bill.updated outbox events are committed together and replayed idempotently. Reducing a bill below already-paid funds requires refund review.
33. Source conflict for forthcoming splits: Backlog US-305 says lock expiry reopens the split, while the architecture state diagram says EXPIRED. Follow the explicit automated acceptance criterion and reopen to OPEN when no payment is in flight, preserving paid shares. The backlog's separate pending bill is represented as a separate pending-balance segment because the provided schema permits one bill/session and the architecture explicitly keeps new orders on that bill with an unchanged locked split.

34. Equal splits apply to the unpaid balance, use a persisted 0-based slot index and the source's deterministic remainder rule, with the schema's 50-payer maximum. Zero-value slots require no provider payment and must be labelled accordingly in the payment UI. Unpaid OPEN recalculation creates a new draft and cancels the old one; paid drafts cannot be silently replaced.
35. Billing child tables gain explicit venue/session scope keys and composite foreign keys rather than relying on unscoped identifier lookups. A database trigger rejects allocations of items outside that scope. Existing rows are backfilled from their authoritative parents and slot order is stabilized by creation time/ID. This migration has not been executed against local PostgreSQL because the runtime is unavailable.

36. Itemized PUT updates only the supplied shares. The creator may initialise unbound shares for same-session participants to support the architecture example, but cannot subsequently release another participant's owned share. Exact unchanged entries are permitted for safe retries. Claiming a slot is atomic and does not change its amount. All allocation writes recheck session activity under the venue transaction.
37. Partial itemized claims do not consume all proportional extras prematurely: floors are assigned to claimed bases, and the largest-remainder completion runs only when all base is allocated. The API exposes unassigned base separately from unassigned gross. Prior paid item portions are subtracted through a venue/session-scoped SQL aggregate. A remaining fee-only balance uses EQUAL rather than pretending it has unclaimed items. Schema legacy/paid-ledger discrepancies fail for review.

38. Split writes explicitly acquire the scoped PostgreSQL split row FOR UPDATE in addition to the venue advisory lock, as required by the supplied allocation trigger. Confirmation checks current bill version and optionally split_revision; the guest UI must send both to avoid confirming changed allocations. Repeated lock requests return SPLIT_ALREADY_LOCKED rather than extend the deadline.
39. An EQUAL lock assigns immutable base-item portions to shares by exact largest-remainder apportionment, then stable item-ID order. This is an accounting allocation, not a claim about who ate an item. ITEMIZED retains explicit claims. Frozen snapshots support subsequent payment/receipt work; provider integration must reconcile those snapshots rather than live menu prices.
40. Lock expiry checks run on relevant requests and in a separately deployed pg-boss worker every minute (bounded batches of 100, scoped mutation under locks). INITIATED/PENDING transactions or PENDING shares hold the lock. A successful unlock cancels the draft while preserving paid records; remaining-balance recalculation creates a new split. Staff unlock authorization and deployed worker verification remain delivery gaps. Background database enumeration is restricted to trusted worker code, never an API-supplied venue scope.
